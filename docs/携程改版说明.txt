一、架构前后对照
----------------------------------------------------------------

【重构前】
- tripcraft/api/app.py：1690 行，约 72 KB。**全部 90+ 条路由、36 个请求模型、全部服务单例
  都塞在 create_app() 一个函数里**，用闭包互相引用（get_llm / get_tools / get_guard /
  get_director / get_call / get_plans / get_deliverables 全是嵌套函数）。
  后果：任何域改一条路由都要动同一个文件，多人并行必然互相踩；无法分工。
- 请求 DTO 与路由混在一起；没有独立的安全边界层。
- 前端 frontend/src/components/StepBar.vue 直接平铺渲染 S0–S12，作为一级导航。
- frontend/src/stores/user.ts 默认 u-demo，靠 localStorage 切换用户；后端多处接受调用方
  任意 user_id，**没有任何服务端认证**。
- frontend/src/demo/{fixtures,beats,driver}.ts 拦截 axios 改写回复、遇错 optional 静默跳过。

【重构后】
- tripcraft/api/app.py：**收敛为约 40 行的组合根**，只做四件事：
  构造 AppContext → 挂中间件 → 注册各域路由 → 托管前端产物。文件内已写明「不要再往本文件加路由」。
- tripcraft/api/context.py【新增】：AppContext 取代 create_app 的闭包单例。
  单例：runs / profiles / s2_sessions / store / practice / tools / guard / director /
  call_svc / supplier_svc / finance_svc / deliverable_svc / plan_svc；
  惰性 getter：get_llm / get_threads / get_deliverables / get_plans / get_tools / get_guard /
  get_director / get_call / get_finance / get_supplier / get_auth。
  构造顺序即依赖顺序，保证 director 与 practice 的绑定只有一份（避免同一 app 内两套状态）。
- tripcraft/api/schemas.py【新增】：36 个公开请求 DTO 集中一处（由 app.py 机械拆出）。
- tripcraft/api/routers/【新增】：按业务域拆成 7 个路由模块，每个暴露 build(ctx) -> APIRouter：
    core.py         参考数据：健康检查、文化桥、翻译、公开契约（steps/dimensions/skill-points/rubric/markets）
    runs.py         训练与评测：Run 状态机 + S2 垂直切片
    practice.py     实战旅程：订单、派单、通关动作、完成条件、导演总线、覆盖与复核
    deliverables.py 交付物：契约渲染、校验、PDF、按对象投递、方案版本与模板、附件
    calls.py        通话与沟通：订单绑定通话、语音中继 WebSocket、IM 群聊与联系人
    growth.py       身份与成长：学习地图、技能点线程、实战评分与画像、初始测评与刷新
    platform.py     平台：工具台、拦截网、校准集、MCP 调试面
  routers/__init__.py 的 ROUTER_MODULES 是唯一注册入口，并写明每个模块的 write scope 归属。
- tripcraft/api/security.py【新增】：认证边界层，把「请求 → 可信 user_id」集中到一处。
  HTTP 中间件默认 fail-closed（TRIPCRAFT_AUTH=on）；公开路径白名单（健康检查、/auth/*、
  /contracts/*、/learn/culture-bridges、/deliverables/specs、/profile/quiz）；
  另有 websocket_user()（WebSocket 无中间件覆盖，自行取 token）与 own_order()（订单归属校验）。
- tripcraft/contracts/stages.py【新增】：**六阶段共享契约 v1**，成为唯一阶段口径来源。
  六阶段 ← S0–S12 映射（13 个内部步骤保留为底层考核状态，只对用户收敛）：
    行前1 需求确认单 ← S0 初始化/交底、S1 抢单、S2 首呼、S3 需求确认
    行前2 行程方案   ← S4 询价与资源取舍、S5 逐日行程
    行前3 报价与成交确认 ← S6 报价与利润、S7 反馈迭代、S8 成交与合同
    行前4 出团通知书 ← S9 资源锁定与行前准备
    行中服务         ← S10 执行与突发处理
    行后复盘         ← S11 结算回访、S12 评分与能力更新
  并把四份文档（及另外四份内部单据）的 code 绑定到阶段：
    requirement_sheet→行前1；resource_quote/itinerary→行前2；quotation/contract→行前3；
    departure_notice→行前4；settlement/review→行后复盘。
- tripcraft/storage/db.py、services/*.py 保持业务实现不变，仅由上层拆分受益。

【拆分方式的取舍】
- app.py 的拆分由 Lead 用一次性脚本完成机械搬运（scripts/_split_api.py，交付前删除）：
  按 tokenize 只改写 NAME token，不碰字符串与注释，因此路径字面量、提示词全量不受影响。
- 拆分后立刻做装配检查：python -m compileall 通过；create_app().openapi() 注册 99 条路径、
  无重复 operationId（修掉了一处 /contracts/markets 被两个域重复捕获的问题）。
- **不做整站推倒重写**：所有既有业务服务（PracticeService、DeliverableService、PlanService、
  FinanceService、SupplierService、CallService、DirectorService、GuardService、ToolsService、
  ThreadService）与既有数据库表全部沿用。


二、当前实际入口
----------------------------------------------------------------

前端（生产构建）：cd frontend && npm run build   （= vue-tsc --noEmit && vite build）
单容器模式：设 SERVE_WEB=1 后由后端托管 frontend/dist

认证开关：TRIPCRAFT_AUTH 默认 on（强制）；仅自动演示/本地调试可显式设 off（会放宽为 X-User-Id 直通）
MCP 调试面：默认隐藏（404），需显式 TRIPCRAFT_MCP_DEBUG=1 才可见；且从不接入真实预订
